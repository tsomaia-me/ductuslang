## 1. Mission

M0 proved the six-step commit against a graph of pure `input` + `derived` cells:
values move, dirt propagates, order is deterministic, the trace is a golden. Every
cell in that slice is **atemporal** — its value is a function of this commit's
inputs and nothing else — and **unconditional** — it evaluates whenever a
dependency changed, always.

M1 breaks both properties. It is the milestone where the runtime learns:

- **time** — a cell may read its own past (`recurrent`), or land a value in a
  *later* commit than the one that asked for it (`deferred`);
- **conditionality** — a subtree may be switched off, hold frozen values, and
  rejoin the live DAG on an edge (`gate`).

Step 4 (`advance_recurrents`) is empty in M0 and exists precisely so M1 has a
place to land (M0.md R23). The M1 mission is to fill it, to give step 1 its
general form, and to make activation a real question for the first time.

The two remaining constructs of STRATEGY §3's M1 sentence — `wire` and `stream` —
are **parked** (R70): the corpus does not define what a wire propagates or when
engagement runs, and the stream corpus contradicts itself in four places. They
become the successor milestone whose first half is corpus work, not code (§2.3).

The M0 doctrine carries forward unchanged: hand-written `.duir` only, no
frontend, stub behaviors through the provider seam (STRATEGY §4a-1), every
semantic claim asserted by a commit-trace golden, every corpus contradiction
filed as a FINDING and ruled by the owner before code (STRATEGY §2.3).

## 2. The slice — RULED cut B (`recurrent` + `deferred` + `gate`)

**RULED R70** (owner, 2026-08-23: *"Temporal + gates"*).

### 2.1 Why the constructs split this way

The four constructs of STRATEGY §3's M1 sentence are not independent, and the
dependency order is not symmetric:

- **`recurrent` depends on nothing.** It needs step 4's body, per-cell history
  storage, and an argument-passing rule for the injected past values (R71).
- **`deferred` depends on nothing structurally**, but shares one mechanism with
  gates: *a dirty root that is not a host write*. Both need step 1's general form.
- **`gate` depends on nothing, and everything depends on it.** Effective
  activation is a property every other construct must consult. Building gates
  last means retrofitting an activation test into finished constructs.
- **`wire` depends on gates and cannot be built at all under the current corpus** —
  §13.10.2 (the six commit steps) contains the string "wire" zero times, and the
  corpus never states what a wire propagates. See §8.4 / FND-34.
- **`stream` depends on gates** and is the largest single construct, with a corpus
  that is detailed and **internally contradictory** — four flat contradictions plus
  an observation-cell surface that does not type-check under the language's own
  casting rules. See §8.5 / FND-35.

One line: **gates are the hub, recurrent is the isolate, streams are the bulk,
wires are the unknown.** Cut B is the largest cut that is buildable today.

### 2.2 What cut B buys

Three constructs, three pairwise questions (recurrent×gate, deferred×gate,
gate×gate nesting) — all askable and answerable in the same milestone, while the
matrix is still small. It converts step 1 from "compare staged inputs" into its
general form — dirty roots arriving from host writes, gate transitions and
deferred landings through **one rank-ordered walk** (R76) — which is the shape
every later milestone needs anyway. And it honors STRATEGY §3's headline: step 4
gets its body.

### 2.3 The parking rider — wires and streams

Wires and streams are a **named successor milestone**, not an unscheduled
backlog. Its first half is corpus work: the wire runtime semantics do not exist
to be implemented (FND-34, MILESTONE-BLOCKING at two entries), and the stream
corpus needs a repair round before it needs an implementer (FND-35). No M1 code
anticipates either construct; the loader keeps rejecting both with a named
diagnostic (§5.4).

*Cadence default (naming only, veto standing): the successor milestone is called
**M1b — wires and streams**. The name is a label for the parked work; its plan
document is written when the corpus round opens.*

## 3. Architecture deltas — what each crate gains

*Grounded in the landed M0 code. File paths are absolute-from-`packages/ductus-lang/`.*

### 3.1 `ductus-ir` — one grammar change (R71) and nothing else

The `.duir` text form is **already complete** for all five entry kinds and all
five cell kinds: Chunk A landed `CellKind::{Input,Derived,Recurrent,Deferred,Fold}`,
`Cell.depth`, `Cell.gate`, `Cell.init`, and the `Gate`/`Wire`/`Stream`/`Effect`
entry structs with every grammar field
(`crates/ductus-ir/src/graph/{cell.rs,cell_kind.rs,gate.rs,wire.rs,stream.rs}`).

**The one change, and it is load-bearing.** The IR text form had no syntax for a
history-offset read: `Cell.inputs` is a flat `Vec<CellPath>`, while IR_GRAMMAR
§5's own worked example lowers

```
recurrent total: i32 = total.past(1, 0) + count
```

to a behavior taking **two** parameters while `inputs` names **one**. R71 closes
that hole: the `cell` production gains `('lookback' lookback_map)?` and
`('fallbacks' fallback_map)?`, and the behavior ABI's argument order is pinned.
The full law is §4.9. The parser, AST and emitter grow the two clauses; nothing
else in `ductus-ir` changes.

### 3.2 `ductus-runtime/src/loader/` — new roles, new checks

- `cell_role.rs` — `CellRole` is a two-variant enum (`Input{init}`,
  `Derived{behavior,inputs}`). It grows `Recurrent` and `Deferred` variants and
  the gate's own node representation.
- `load.rs` — the slice checks at `admitted_kind` / `admitted_entry` relax by
  exactly the rows cut B admits, and each admitted construct gains its clause
  law (which clauses a `recurrent` requires vs forbids, and so on) in the same
  shape as the existing `input_clauses` / `derived_clauses` pair.
- `loaded_graph.rs` — `static_order` currently holds **derived cells only**
  ("every DERIVED cell — inputs are written, never evaluated"). Recurrents join
  it (§4.2); deferreds do not; gate predicates are **not** static-order nodes at
  all — they run in step 1a (R73).
- **New loader checks per construct** (§5) — the cycle check in particular:
  M0 rejects every derived→derived cycle, and a recurrent reading its own past
  is *supposed* to break a cycle legally, so `static_order`'s Kahn pass must drop
  history edges from the cycle graph (RW-4). This is the check most likely to be
  got subtly wrong.
- **One order, not two (R80 item 4).** Only self-history and `lookback` edges are
  dropped from ordering. A recurrent → reader VALUE edge orders CONSTRUCTION
  exactly as it orders step 3, so **construction order = static order**: a reader
  constructs after its recurrent, the allocation placeholder is genuinely
  unobservable, and no separate construction order is kept beside `static_order`.
  The one exception is the deadlock RELEASE a read-cycle forces, and the set of
  nodes it can release is wider than the cycle — see FND-40 and §4.12's
  construction paragraph.

### 3.3 `ductus-runtime/src/store/` — the biggest single change

`CellStore` (`store/cell_store.rs`) is exactly three flat `Vec<Value>` of length
`cells.len()`: two committed buffers plus staged, with a live index flip. Every
cell has **one** slot per buffer.

- A `recurrent depth N` needs N+1 values (current + N past), and each `lookback`
  entry needs K more for its input. Either the store grows a second, ragged
  region (a per-cell history ring outside the flat buffers) or the flat buffers
  become ragged. **This is a rework of `CellStore`, not an extension** — see §7,
  and R78's storage call (fork 7, cadence: a separate region + per-cell rings).
- `Snapshot::read(&CellPath) -> Result<Value, _>` returns one value per path.
  History stays invisible to it (R78, fork 8): witnesses assert history through a
  derived that reads `.past`, which is exactly how a program observes it.
- Frozen values under a closed gate need no new storage — a frozen cell is simply
  one that never gets written — but `begin_pending`'s wholesale
  `copy_from_slice(live)` is what makes freezing free, and that is pinned as a
  deliberate property (§4.7), not left as an accident.

### 3.4 `ductus-runtime/src/engine/engine.rs` — where each step grows

The six functions are `dirty_set` / `evaluation_order` / `evaluate` /
`advance_recurrents` / `publish` / `clear_dirty`, in step order, exactly as R23
demands. The deltas:

| Step | M0 body | M1 delta |
|---|---|---|
| 1 `dirty_set` | walks cells in rank order; dirties an `Input` whose staged ≠ committed | **1a** evaluates every gate predicate against prior-commit values and records effective-activation transitions (R73); **1b** walks ONE rank-ordered sequence with all root sources interleaved — host writes, gate transitions, deferred landings, and **last commit's recurrent advances** (R76; the advance root, §4.12/R80). |
| 2 `evaluation_order` | returns `&graph.static_order` verbatim | unchanged in shape; recurrents are already in the order. Eligibility (activation) is tested in step 3, not by filtering here. |
| 3 `evaluate` | evaluates a derived iff any direct dependency is dirty; result to pending; dirty bit = value changed | gains: an **activation test before the staleness test** (§4.3); a recurrent's argument gather reads history rings as well as pending; a recurrent's result is HELD, not written (step 4 writes it), and its advance sets **no dirty bit this commit** — it is a root at the next one (§4.12). |
| 4 `advance_recurrents` | `fn advance_recurrents() {}` | **the body lands here.** Drains the holds: ring shift + current write, once per evaluation (R72 + R77). Its position — after evaluate, before publish — is what makes lockstep true. |
| 4½ deferred dispatch | — | **new phase between step 4 and step 5** (R74a): a deferred whose provenance is dirty this commit evaluates synchronously over the pending values and HOLDS `(value, due = commit_index + depth)`. |
| 5 `publish` | `store.flip()` + `publish` event | unchanged. `publish` stays the last value-bearing line of a commit block. |
| 6 `clear_dirty` | `dirty.fill(false)` | unchanged. A gate transition is a root like any other and its bit clears with the rest. |

`invoke()` — the single behavior-call path — gathers arguments as
`inputs.iter().map(|&i| store.pending(i))`. A recurrent's extra past arguments
are not expressible in that map; R71's ABI order (§4.9) is the replacement.

### 3.5 `ductus-runtime/src/trace_sink/` — exactly one new event

`TraceEvent` has five variants (`CommitBegin`, `Dirty`, `Eval`, `Publish`,
`CommitEnd`), each with a byte-exact canonical line. R75 adds **one**:
`Gate { path, open: bool }`, rendering `gate <path> open` / `gate <path> close`,
pinned in `trace_event.rs`'s doc comment exactly as the five existing ones are.
Recurrent advances render as `eval`; deferred landings render as `dirty`.

### 3.6 `ductus-conformance` — witness growth

Per-construct witness files under `tests/` (R25), each `#[test]` loading a
`corpus/duir/m1/*.duir` and byte-comparing a `.trace` golden (R9). The new
corpus directory is `corpus/duir/m1/`. Property tests (R4, `proptest`) extend
with the new invariants named in §6.4.

## 4. Semantics contract — the commit steps as they grow

The normative step list is **SPEC §13.10.2**. M0 implemented it with only
`input` + `derived` present. Below, each step is quoted at the clauses M1
activates, and every completion the corpus does not make is annotated with the
ruling that makes it — **fork N as ruled** (the owner's word, §9) or **cadence
default** (executed under LEARNINGS #36, veto standing, disclosed at finish).
Where a ruling and the corpus disagree the corpus wins and the ruling is a
FINDING to be executed LOG-first. **One ruling was in that position and is now
out of it:** R73's rider (§4.7) collided with SPEC §13.9.6 and
022-36/37/38/39/022-55, which permit the read it rejected. The owner ruled the
fork **(a)** on 2026-08-24 — *"(a) continue."*, quoted in GATE.md — so the
load-time rejection is **WITHDRAWN**: a gate predicate reading cells its own gate
guards is LEGAL, the `gate_predicate_reads_guarded` check and its `DiagClass`
member are deleted from the tree, and FND-36 closes RULED (a). Every ruling below
is now clear of the corpus.

**The M1 commit cycle, in order:**

```
1a  evaluate every gate predicate against PRIOR-COMMIT values; record
    effective-activation transitions                        (R73, fork 3 as ruled)
1b  one rank-ordered walk fixes the dirty roots — host writes, gate
    transitions, deferred landings, and LAST COMMIT'S recurrent
    advances, interleaved by rank            (R76 fork 6 as ruled; R80 §4.12)
2   evaluation order = the static order (recurrents included)
3   evaluate: activation FIRST, then staleness; derived results -> pending,
    recurrent results -> HOLD
4   advance recurrents: drain the holds, ring shift + current write
                                                        (R72 + R77, forks 2 and 9)
4½  deferred dispatch: evaluate synchronously, hold (value, due)
                                                             (R74a, fork 4a)
5   publish: the snapshot flip; `publish` is the last value-bearing line
6   clear dirty bits
```

### 4.1 Step 1 — the general form, and the predicate pre-pass

§13.10.2 step 1, verbatim on the parts M0 could not reach:

> "Dirty propagation extends to all derived cells transitively dependent on
> dirty roots, and to all recurrents whose triggers fired this commit."

> "In step 1, a deferred run **landing** this commit (dispatched `N` commits ago)
> is a dirty root, taking its place in step 1b's rank-ordered walk alongside the
> host writes and the gate transitions: consumers evaluate over it in steps 2–3
> exactly as over a changed signal; if the run due at this commit is unfinished,
> the commit waits for it at this fold-in before proceeding — the publication
> barrier."

*(That second quote is the post-batch §13.10.2 — the sentence this plan originally
quoted, "the landed value is folded in", was rewritten by the corpus batch this
plan authorizes. Quotes here are re-verified against the landed corpus, not
against the pre-batch text.)*

**Step 1a — the predicate pre-pass. RULED (fork 3 as ruled, R73).** Every gate
predicate evaluates in a pre-pass at the head of step 1, against **prior-commit
values** — the live buffer as it stands at commit start. The resulting
effective-activation transitions then join the dirty roots in 1b. The corpus's
unqualified sentence — *"the gate predicate itself keeps reading prior-commit
values"* (023-57; the two SPEC sites that carried it, §13.9.7 and §13.9.8, were
rewritten by this batch to route it through step 1a) — is
taken **literally**: a staged input write publishes at commit N and the predicate
sees it at commit N+1, so the flip and its same-commit snap happen at N+1. This
is the reading that leaves §13.10.2's own invariant — *"No new dirty bits are
added during the rest of the commit cycle"* — true without reinterpretation.

**Cadence default (C-50, veto standing):** a gate's boolean occupies **no graph
cell**. The engine holds per-gate state internally. The predicate is a pure
function over live values, so evaluating it every commit for every gate — in rank
order — is unobservable, and that is what the engine does: no dirtiness test
gates the pre-pass, only the transition it computes matters.

**Cadence default (C-39/C-40, veto standing):** an inner gate's own predicate
still evaluates under a closed ancestor, and its **own** state updates. What the
trace records is the **effective**-activation transition (own AND every ancestor
via `gate_parent`): the `gate <path> open|close` line appears only when effective
activation changes, the gate-open snap applies only on an effective open, and an
ancestor's reopen restores each descendant to its own state without replay.

**Step 1b — one rank-ordered walk. RULED (fork 6 as ruled, R76).** The dirty
roots are fixed by a single walk in rank order with **all root sources
interleaved by rank** — gate transitions, deferred landings, host writes. The
trace's root lines are therefore one rank sequence whatever produced them, and a
reader cannot tell a landing from a host write. That is deliberate: a downstream
consumer cannot tell either, and the trace is the consumer's view (R24, R75).

**The publication barrier is vacuous in a sequential core.** M0.md R1 already
ruled the rendering: *"evaluate at dispatch, hold, publish at dispatch+N — the
as-if law makes the sequential rendering exact."* A run that "is unfinished"
cannot happen when the run finished synchronously N commits ago. The held value
folds in unconditionally at step 1b of commit `dispatch+N`. Nothing waits.

**Cadence default (C-20/C-21, veto standing):** ordering among several landings
at one commit is the fork-6 rank walk — landings fold in by rank like every other
root; ordering among several dispatches at one commit's end is rank order too.

### 4.2 Step 2 — the per-commit DAG gains recurrent nodes and loses gated edges

> "Each recurrent whose expression became dirty this commit. A recurrent
> contributes one DAG node per cell (or one node per tuple group for
> tuple-coupled recurrents, §13.2.4.6)."

> "Edges are dependencies; recurrent self-history reads (`.previous`/`.past`) are
> treated as inputs at their previous-committed values, which breaks reactive
> cycles."

And on deferred, decisively:

> "The cell's own body is never a step-2 DAG node."

**The law of the plan.**

1. **Recurrents join `static_order`** and take their rank from graph-section
   entry order like any other entry (R67 unchanged). A recurrent evaluates when a
   **value** input is dirty — exactly like a derived. Self-history edges and
   `lookback` edges are **not cycle edges** and **not staleness triggers**.
2. **Deferreds do NOT join `static_order`.** A deferred's body is never a
   schedulable node; its *value cell* holds the last published value, is a root
   at step 1b on the landing commit, and is a leaf everywhere else.
3. **Gate predicates are not `static_order` nodes either** — they run in step 1a
   (R73). Their `inputs` are ordinary graph cells and their dirtiness is what
   makes a transition possible, but the predicate is not scheduled with the DAG.

**Cadence default (C-45, veto standing):** a `gate` entry takes graph-section
entry rank exactly like every other entry — 033-260's letter, applied without a
carve-out.

### 4.3 Step 3 — activation first, staleness second, recurrent results HELD

> "Recurrent self-history reads (`.previous`/`.past`) → previous-committed
> values, always (lockstep — §13.2.4.1)."

> "Derived behaviors write their results into the pending snapshot. Recurrent
> expression results are held aside (not yet visible to in-pass evaluation) until
> step 4."

**The law of the plan.**

1. **Activation is checked BEFORE staleness.** A cell that is not effectively
   active is ineligible this commit even with dirty dependencies (§4.7). M0's
   sole gate on evaluation — `dependencies(cell).iter().any(|i| dirty[i.0])` —
   grows a conjunct, and the frozen-value law rests on the order of the two tests.
2. **A recurrent's result is HELD**, not written to pending: a derived scheduled
   after a recurrent in the same commit that reads that recurrent sees the
   *previous* value, which is what `store.pending()` already returns when nothing
   wrote it. The hold-aside buffer is the whole mechanism.
3. **History reads resolve from the rings** — prior-committed values, always,
   for self-history and for `lookback` input history alike.
4. **A recurrent's evaluation sets NO dirty bit for this commit's staleness
   test.** A reader whose only dirty dependency is an advancing recurrent does
   not evaluate at this commit, whatever the declaration order; the advance is a
   dirty root at the NEXT commit instead — **§4.12**.

### 4.4 Step 4 — the body, at last, and the advance cadence

> "**Advance recurrents.** Write the next values computed in step 3 into the
> recurrent cells. After this step, recurrent reads return their newly-advanced
> values."

and the lockstep law it realizes, §13.10.3:

> "Recurrent expressions across multiple recurrent cells evaluate in lockstep
> (§13.2.4.1); no internal ordering between them is observable, because none of
> them sees another's just-advanced value."

**RULED (fork 2 as ruled, R72): history rings shift PER-ADVANCE.** A commit in
which the recurrent does not evaluate consumes no slot. `past(k)` therefore means
"k advances ago", not "k commits ago" — §13.2.4.1 is the normative home of
advancement and it makes advancement conditional in the same breath that it
defines it.

**RULED (fork 9 as ruled, R77): evaluate ⇒ advance**, even when the result is
bit-identical to the current value. The ring shifts exactly once per evaluation.
Value-change gating governs **downstream propagation only** (§13.2.4.4's sentence
is explicitly about propagation), so a repeated value still consumes a slot and
`past2` never depends on whether an intermediate value happened to repeat.

Together R72 + R77 give one sentence: **the ring shifts exactly once per
evaluation, and never otherwise.**

Because every recurrent's read resolved against the pre-advance state in step 3,
the order in which step 4 drains the holds is **unobservable** — the property the
lockstep law promises, asserted directly by a property test (§6.4).

**What the advance makes visible to CONSUMERS is a next-commit event** — the
advance-root law, **§4.12**.

### 4.5 Step 4½ — deferred dispatch, and the readiness surface

The pre-batch §13.10.2 read:

> "At the commit's end — after evaluation has settled, so the values being
> published are known — a deferred cell whose provenance is dirty this commit
> **dispatches**: its inputs are snapshotted from this commit's newly committed
> values and its behavior is scheduled off the driving context."

That is the sentence whose two clauses pointed in opposite directions (C-19), and
the corpus batch replaced it with the ruled position:

> "A deferred cell whose provenance is dirty this commit **dispatches** at a
> pinned position in the step list: *after* step 4's recurrent advance and
> *before* step 5's publish. Its inputs are therefore snapshotted from exactly the
> values this commit is about to publish, the recurrent advances included, and its
> behavior is scheduled off the driving context; `publish` remains the last
> value-bearing act of the commit."

> "Both landing and dispatch follow value-change semantics, and the two ends of a
> deferred's life sit at opposite ends of the commit."

**RULED (fork 4a as ruled, R74):** dispatch happens **after step 4 and before
step 5's flip**. "After evaluation has settled" was the operative clause of the
pre-batch text, and it is the only reading under which `publish` remains the last
value-bearing line of a commit block. Under M0.md R1's sequential rendering, dispatch means: evaluate
the behavior **synchronously** over the pending (newly-committed) values, then
HOLD `(value, due = commit_index + depth)`. Nothing waits; the publication
barrier is vacuous (§4.1).

**RULED (fork 4b as ruled, R74):** the readiness surface is exactly

```rust
pub fn has_staged_work(&self) -> bool   // true iff a held deferred run has not yet landed
```

`commit()`'s signature is **untouched** — 027-128 says the surface is "the same
surface as queued writes", and queued writes are queried, not returned from
`commit`. Nothing more lands in M1: no scheduler, no callback, no return type.

**Cadence default (C-28, veto standing):** a deferred's provenance is dirty iff
**any of its input cells MOVED this commit** — the per-input reading, not a
bitwise comparison of the whole snapshot tuple against the previous dispatch's
snapshot. This composes with R65's bitwise gating: every bit read here is already
bitwise.

**The bit that answers "moved" is not the same bit for every kind (FND-39).** A
recurrent answers with the `advanced` bit step 4 has just written; every other
kind answers with its dirty bit. They are not interchangeable at this position:
§4.12 sets a recurrent's dirty bit at the commit AFTER the advance, so reading it
here would ask about the previous commit's advance while the arguments come from
this one's — an advance would be dispatched a commit late, over the value that
later commit advanced to, and a commit that rooted without advancing would
dispatch again over a value that had not moved. 023-73's own words are the test:
*"the run snapshots exactly the values the commit is about to publish, recurrent
advances included."*

So a **deferred sees an advance one commit earlier than a derived does**, and that
is the same law rather than an exception to it. A derived reads in step 3, which
runs before the advance, so §4.12 delays it a commit to keep the schedule out of
declaration order's hands. A deferred reads at a fixed position after step 4 that
no declaration order can move, so it needs no delay and is given none. Each
advance reaches a deferred exactly once, in advance order.

**Cadence default (C-29, veto standing):** a **landing this commit counts as
provenance-dirty** for a downstream deferred dispatching at this commit's end.
Chained deferreds therefore compose their latencies additively, which is what
023-18 assumes without writing it.

**Cadence default (C-23, veto standing):** at construction a deferred evaluates
**synchronously, like a derived** (016-298's startup evaluation), giving the cell
its startup value; the normal dispatch cadence applies from the first commit
onward. There is no `init` clause on a deferred and none is added.

### 4.6 Steps 5 and 6 — publish, clear

Step 5 is unchanged in shape: `store.flip()` plus the `publish` event. Step 6
fills the dirty bit vector with `false`. A gate transition is a dirty root
(§13.10.2 step 2), and a root is cleared with the rest — the per-gate activation
STATE persists across commits (it is not a dirty bit), while the *transition* is
per-commit and dies at step 6.

### 4.7 The freeze law — what a closed gate actually does (§13.9.7 Model B)

Gates gate **propagation, never existence**: §13.9 — *"a gated instance is
constructed unconditionally … and, while inactive, is **frozen** under Model B
(§13.9.7) — its cells hold their values and resume when the gate reopens. Gates
never unmount or reconstruct an instance."* The per-kind behavior, verbatim from
§13.9.7:

| Kind | Under a closed gate |
|---|---|
| Input cells | *"stay live. Wires delivering into the gated node still write their values into the destination's input cells."* — writes stage, `dirty` lines appear, guarded deriveds do not recompute |
| The `when` predicate | *"re-evaluates whenever any cell in its provenance set changes."* — in M1 it evaluates every commit in step 1a (C-50) |
| Deriveds | *"do not recompute. They hold their last committed value."* |
| Recurrents | *"do not advance. They do not re-evaluate; the cells hold their last committed value. Any input change that would have triggered re-evaluation during a gated period is **lost** — the runtime does not queue triggers, and gate-open does not replay them."* |
| Deferreds | *"do not dispatch; gate-close cancels any in-flight runs — no publication, no barrier — and the frozen cell serves its last-published value."* On gate-open the snap **dispatches** a fresh run rather than evaluating synchronously — landing at +depth |
| Outputs | *"do not propagate."* |

Reads are always defined: §13.9.7 — *"reads return frozen values: the last
committed value during an active period, or the initial value if the instance has
never been active."* Never `Option[T]`.

**Effective activation** (§13.9.7): *"An instance is *effectively active* iff its
own gate AND every ancestor gate on the path from the root are open. Closing any
ancestor gate transitively freezes every descendant … Reopening an ancestor
restores each descendant to *its own* gate state."*

**On an effective open**, the guarded deriveds evaluate **in that same commit** —
forced-stale, reading current values (022-59: *"The gate-open re-evaluation snap
is scheduled within the **same commit** that flips the predicate false→true — not
the next commit."*). Under R73's pre-pass the flip is known before step 1b ends,
so the snap needs no second pass.

**Freezing is FREE in M0's store shape**, and that is pinned as an intended
property rather than an accident: a frozen cell is one that nothing writes to
pending, and `begin_pending`'s wholesale `copy_from_slice(live)` already leaves
it holding its last committed value. A comment and a witness carry the claim.

**Cadence default (C-13, veto standing):** `reset_on_reopen` clears self- and
input-history when the reopen transition is detected in **step 1a**, before step
3's reads — so the first post-gap evaluation reads **fallbacks**, exactly as
§13.2.4 requires (*"clears the self- and input-history … so the first post-gap
evaluation reads fallbacks"*).

**What an INPUT-history reset falls back TO — the landed behavior, ledgered
(wave 2, veto standing).** §13.2.4 says the reset makes the first post-gap read a
fallback read, but the text form seeds **self**-history only: `init`/`fallbacks`
(033-267/033-268) are the recurrent's own ring, and a `lookback` ring has **no
fallback spelling in the IR at all**. So "reads fallbacks" has no referent for an
input ring, and the build must still answer. **It answers with the input cell's
construction-era value:** `seed_input_history` fills each `lookback` ring's
fallback area with the input's construction value — the only value of that cell's
type the runtime holds at that moment — and `clear_history` empties the rings, so
a post-reset read lands back on it. This is a **stand-in for an unspellable
fallback**, not a ruled semantics: the general question (non-literal and
per-input fallbacks) is FND-28's open sub-fork, and this paragraph is that
sub-fork's runtime residue recorded in the open rather than left in a code
comment.

**The rider that is not a default — the predicate's own reach. RULED (a) BY THE
OWNER, 2026-08-24; the rejection is WITHDRAWN; see FND-36.** R73's rider had said
a gate predicate that reads any cell **inside its own guarded subtree** is

### 4.8 The lossy gap is a witness obligation

*"Any input change that would have triggered re-evaluation during a gated period
is lost"* means a closed gate is genuinely lossy for recurrents. A frozen
recurrent's pre-gap value holds until a **new** trigger fires after the reopen —
the reopen alone does not resume the missed advance. §6.3's witness 7 asserts the
loss, not merely the freeze.

### 4.9 The recurrent serialization and the behavior ABI — RULED (fork 1 as ruled, R71)

The `.duir` `cell` production gains **two** clauses — `lookback` (per-input
history depths, reusing the existing `lookback_map` production) and `fallbacks`
(a per-`k` fallback map):

```ebnf
cell          ::= cell_kind PATH ':' type_tag
                  ('uses' BID)? ('inputs' path_set)? ('depth' INT)?
                  ('lookback' lookback_map)? ('reset_on_reopen')?
                  ('init' value)? ('fallbacks' fallback_map)?
                  ('gate' PATH)? ('combiner' BID)? ('else' value)?
                  ('members' member_set)?

fallback_map  ::= '[' (INT ':' value (',' INT ':' value)*)? ']'
lookback_map  ::= '[' (PATH ':' INT (',' PATH ':' INT)*)? ']'   // unchanged, §15.4.6 / 033-117
```

Clause order is the production's order, each clause at most once — the existing
law, extended by two positions.

**What a `fallbacks` key means.** Key `k` is the value a `.past(k)` read returns
**before `k` advances exist**. The corpus's own two-fallback example becomes
serializable:

```ductus-ir
recurrent App.fib : i64 uses B@d8 inputs [] depth 2 fallbacks [1: 1, 2: 0]
```

**One meaning, one spelling.**

- `init v` is the **uniform shorthand**: every depth `k` falls back to `v`.
- `fallbacks [...]` is the **general form**.
- On a `recurrent`, **both present is a LOAD error** (§5.1).
- **Canonical emission** writes `init` when all depths share one value, and
  `fallbacks` otherwise. Round-trip byte stability is preserved because the
  choice is a function of the values alone.

**Fallback values are LITERALS only.** A non-literal (PATH) fallback —
`count.previous(start_value)`, the corpus's canonical source idiom — is a
**FILED sub-fork, deferred** (FND-28's open half). It is not a blocker: a PATH
fallback is a dependency edge, which is a language-level question, not a
serialization one. M1 ships the literal form and the sub-fork stays open.

**The behavior ABI argument order** — the pinned law, in one list:

1. **inputs**, in `inputs` list order;
2. **self-history**, `past1 … pastDepth`, ascending `k` (`past1` FIRST);
3. **per `lookback` entry, in `lookback` list order**: `<input>_past1 … <input>_pastK`, ascending `k`.

```ductus-ir
recurrent App.avg : f64 uses B@d7 inputs [App.x, App.y] depth 2 lookback [App.x: 3] init 0
behavior  B@d7 (x, y, past1, past2, x_past1, x_past2, x_past3) -> f64 { … }
```

Arity is therefore `inputs.len() + depth + sum(lookback values)` — the ABI law,
which the behavior stubs and the store's argument assembly both obey. The
LOAD-TIME CHECK of it is **deferred (FND-37)**: a behavior is an opaque closure
across the D5 provider seam, so the expected arity is computable and its
counterpart is not. A wrong-arity stub fails as a D8 trap naming its cell.

**Depth defaults — cadence defaults (C-7/C-8, veto standing):** an omitted
`depth` defaults to **1** on a `recurrent` **and on a `deferred`** — the landed
corpus says exactly that (016-301: *"an omitted depth on a recurrent is 1, an
omitted depth on a `deferred` is 1"*), mirrored in SPEC §15.4.6 and IR_GRAMMAR
§3. `depth 0` written explicitly on either kind is a **load error** — new class
`invalid_history_depth`.
016-282's "`derived T` IS the N = 0 case" is a statement about the language's
type ladder, not a licence for a `.duir` line that means nothing at runtime.

### 4.10 The M1 trace vocabulary — RULED (fork 5 as ruled, R75)

R24 ruled the trace **minimal-semantic**: "the observable contract only … never
implementation shape". M1 keeps that and adds **exactly one** event kind:

```
commit_begin
gate App.g open           ← the ONE new event kind
dirty App.d 3 -> 7        ← a deferred landing, rendered as the dirty root it is
eval App.r -> 12          ← a recurrent advance, rendered as the value production it is
publish
commit_end
```

- A deferred **landing** reuses `dirty <path> <old> -> <new>` — it IS a dirty
  root by the corpus's own words.
- A recurrent **advance** reuses `eval <path> -> <value>` — it IS the production
  of the cell's value.
- A **gate transition** earns its own line: it is observable (the whole subtree's
  behavior changes), it has no value, and no existing event can express it. Its
  canonical form is byte-exact and one line, like the five existing events:
  `gate <path> open` / `gate <path> close`. It records EFFECTIVE activation
  (§4.1's C-39/C-40 default).

A separate `land`/`advance` event would record *which mechanism produced the
value* — implementation shape, which R24 forbids.

§13.10.3's realized schedule — *"the rank-lexicographic minimum topological order
of the per-commit DAG"* (R67/FND-25) — governs the widened DAG exactly as it
governed M0's. Recurrent nodes and gate entries take their rank from
graph-section entry order like any other entry (C-45). Nothing about M1 reopens

### 4.12 The advance-root law — what a consumer of a recurrent sees, and when

**Cadence completion (wave 2, veto standing; raised at the finish report under
the owner's standing instruction, LEARNINGS #36).** The corpus never says what a
recurrent's advance does to its READERS' schedule, and the wave-1 build answered
it by accident: whether a reader saw the advance depended on **declaration
order** (FND-38). No reading of the corpus permits that, so the law is completed
here and was executed LOG-first as **023-78** in DECISION_LOG.md, mirrored into
SPEC §13.10.2's step 4 (*"Consumers read the advance one commit later"*).

**The law, in one sentence.** A recurrent's advance at commit N — bits-changed
only — makes the recurrent a **DIRTY ROOT at commit N+1**'s rank-ordered root
walk, exactly as a deferred landing does, **except that it renders no trace
line**.

Inside the advancing commit N:

- in-pass readers read the **pre-advance** value — results are held aside, the
  lockstep law (§4.3);
- the recurrent's evaluation sets **no dirty bit** for step 3's staleness test,
  so a reader whose only dirty dependency is an advancing recurrent does **not**
  evaluate at N — under **either** declaration order. That is the point: the
  schedule stops depending on entry rank.

At commit N+1:

- step 1b's root walk sets the recurrent's dirty bit, marking it a **changed
  dependency**. The recurrent itself does not re-evaluate for that — only its own
  value inputs being dirty makes it evaluate;
- its **step-3** consumers evaluate, reading the published (advanced) value;
- cascades follow naturally: a recurrent reading another recurrent advances **one
  commit behind it** — the delay-chain semantics.

**A `deferred` consumer is the one exception, and it is not one (FND-39).** Its
read happens at step 4½ of the ADVANCING commit, not at N+1: the dispatch position
is fixed after step 4 (023-73), so no declaration order can move it and no delay
is needed to make it deterministic. A deferred's provenance therefore asks a
recurrent input for its `advanced` bit rather than its dirty bit — see §4.5.

**Why no trace line.** The change was already observable at commit N as the
advance's own `eval` line, so the observable at N+1 is its consumers'
evaluations, nothing more. A landing renders `dirty` because nothing else in the
trace shows it; an advance does not, because the `eval` line already did (R24 /
R75 — observable contract, never mechanism).

**Idempotence.** Empty-commit idempotence is unchanged for a graph with no
pending advance root. A commit whose only activity is advance-root consumer
evaluation shows those `eval` lines and `publish`.

**The consequence at the boundary: a cycle closed through a recurrent FREE-RUNS.**
Where a recurrent's own reader feeds it back — `self_cycle`'s shape, `acc` reads
`step` and `step` reads `acc` — each advance roots the next commit, that commit
re-evaluates the reader, the reader dirties the recurrent, and the recurrent
advances again. The loop therefore keeps turning after the input stops, once per
commit, forever. That is what a delay loop IS, and it is inside the law rather
than an exception to it: idempotence was only ever claimed for a graph with no
pending advance root, and this graph never has none. What holds unconditionally
is the finiteness law — one evaluation per cell per commit. It is pinned by
`self_cycle`'s golden, which gained a quiescent fourth block to say so (wave-2
cadence, veto standing; before the advance-root law the same graph went quiet,
and the witness's own doc comment said it always would).

**What such a cycle reads at CONSTRUCTION is half-settled (FND-40).** The
ordering pass releases one member and it reads the recurrent's slot before the
recurrent has run. That slot now holds the recurrent's **depth-1 fallback** — the
value §4.9 already defines as what a read yields "before the ring has advanced
that far" — rather than a typed zero, so the value is one the source spells
(cadence, veto standing). WHICH nodes are released is still `rank`-least, hence
declaration order — and the release is **not confined to the cycle**. The test is
"every unmet predecessor is a recurrent read", which a plain reader downstream of
an in-cycle recurrent also passes, so that reader can be handed the fallback
purely because it was declared early, and one cycle can force several releases in
turn. A probe: `App.r` and `App.d` form the cycle, `App.outside` reads only
`App.r`; declared first `App.outside` constructs at `100` (the fallback),
declared last at `201` (the computed value). Same graph, two snapshots, and the
divergent cell never touched a loop. That half is OPEN and needs an owner ruling;
it is the FND-38 class of nondeterminism moved to construction.

**A recurrent may not close the loop on ITSELF.** `inputs [App.r]` on `App.r` is
a self VALUE read, which 016-51 puts behind `.previous`/`.past` alone and which
§13.2.4.1 denies even to those; the loader rejects it as
`recurrent_self_reference` (§5.1). Under this section's law the shape would
otherwise be its own staleness trigger — advance, root, re-evaluate, advance —
turning once per commit with no host activity at all.

**Witness impact.** Every m1 golden was re-derived under this law. Two carry a
reader of a recurrent and **change**: `lockstep_pair`, where `App.b` advances one
commit behind `App.a` — the delay chain made visible — and
`equal_value_advance`, where `App.report`'s evaluation moves one block later and
the equal-valued advance produces no reader evaluation at all, because a
bits-unchanged advance is no root. `self_cycle` reads a recurrent too and its
existing blocks do NOT change — its reader is dirtied by the input every commit,
so the advance root adds nothing there — but it GAINS a quiescent fourth block,
which is where the free-run above became visible and where the golden now pins
it. Every other witness is untouched: no other m1 module reads a recurrent, and a
recurrent with no reader has nothing to delay.

2. **first evaluation.** What `.past(1)` reads before any advance — the fallback
   (§4.9). The very first commit's trace is the whole assertion.
3. **lockstep across a chain.** Two recurrents where one reads the other's
   current value: both advance in the same step 4, so neither sees the other's
   advanced value within a commit (023-35). Under **§4.12** the reader also
   advances ONE COMMIT BEHIND its source — the delay chain — so this witness's
   golden (`lockstep_pair`) changes in wave 2.
4. **self-history is not a cycle.** A recurrent whose only input is its own past
   must LOAD — the `derived_cycle` check must not fire (RW-4). Its own PAST is
   `depth`, never an `inputs` entry: a recurrent naming ITSELF in `inputs` asks
   for its own current VALUE and is rejected as `recurrent_self_reference`
   (§5.1, FND-40), so the two halves of this witness are one load and one
   refusal.
5. **depth > 1 + per-`k` fallbacks.** `depth 2 fallbacks [1: 1, 2: 0]` — the
   corpus's `fib`. Asserts both slots shift by exactly one per advance and each
   `k` reads ITS fallback before `k` advances exist (**R71**).
6. **`lookback` input history.** `inputs [App.x] depth 1 lookback [App.x: 2]` —
   asserts the ABI order (`x, past1, x_past1, x_past2`) and that the input ring
   shifts with the recurrent's advances, not with commits (**R71 + R72**).
7. **bit-identical advance.** A recurrent evaluating to its current value: the
   ring STILL shifts and downstream sees nothing (**R77**). The trace shows the
   `eval` line and no downstream `eval`.
8. **skipped commit consumes no slot.** A recurrent dirty at commits 1 and 3 but
   not 2: at commit 3, `past2` reads the commit-1 value, not a duplicate
   (**R72**). This is the witness that discriminates the two readings of fork 2.
9. **empty commit.** No writes: no advance, no `eval`, `publish` still emitted
   (idempotence, unchanged from M0).
10. **NaN in a history slot.** R65's bitwise law applied to the history ring.
11. **canonical spelling.** `init v` round-trips as `init v`; a recurrent whose
    per-`k` fallbacks differ round-trips as `fallbacks [...]`; a `fallbacks` map
    whose values are all equal canonicalizes to `init` (**R71**). Byte-stability
    gate, plus a load-error case for `init` + `fallbacks` together.
    *This witness has no `.duir`/`.trace` pair and cannot have one:* its third
    clause is about text that is NOT canonical, and every corpus witness asserts
    `emit(parse(f)) == f`. It lives as `ductus-ir` unit tests beside the emitter
    (`text/emitter/emit.rs`), where the non-canonical source is an input rather
    than a file claiming to be canon.

### 6.2 Witness list — `deferred`

1. **latency-1 round trip.** `depth 1`: dispatch at commit N, landing at N+1,
   both visible in the trace — the landing as a `dirty` line (**R75**).
2. **latency-N.** `depth 3`, the value crossing exactly three commit boundaries
   and nothing landing early.
3. **what the cell reads while in flight.** Every commit between dispatch and
   landing reads the last published value; the witness pins it.
4. **the landing is a dirty root.** The landing commit shows downstream deriveds
   re-evaluating from a `dirty` line the host did not stage (**R74a + R76**).
5. **the pipeline.** Inputs dirty at consecutive commits — 023-64: *"Up to `N`
   runs of a `deferred[N]` cell's one behavior may be in flight at once — a
   pipeline yielding full-rate output at N-commit latency"* — so the cell lands
   at EVERY commit, N behind. Asserts full-rate output.
6. **several deferreds landing in one commit.** Rank order, interleaved with host
   writes in the same single `dirty` sequence (**R76 / C-20**).
7. **dispatch gating.** Unchanged inputs dispatch nothing; a landed value equal
   to the cell's current value propagates nothing. Two assertions, both bitwise
   (R65), the first on the per-input dirty-bit basis (**C-28**).
8. **chained deferreds.** A landing at commit N makes the downstream deferred's
   provenance dirty at N's end, so it dispatches at N and lands at N+depth
   (**C-29**). Latency composes additively.
9. **construction value.** A deferred's startup value comes from a synchronous
   construction evaluation (**C-23**); the first commit does not re-run it.
10. **`has_staged_work`.** True between dispatch and landing, false after
    (**R74b**). Asserted around the whole sequence, not by counting commits.
11. **dispatch position.** `publish` is the last value-bearing line of every
    commit block (**R74a**) — the trace shape is the assertion.
12. **sequential-rendering note.** Trace identity against a threaded oracle is
    not buildable in M1 (M1 is sequential), but R1's rendering is STATED in the
    witness comments so the later threaded milestone has an oracle to match.

### 6.3 Witness list — `gate`

1. **closed at startup.** §13.2.6/016-144: predicates evaluate in the startup
   topological order and *"An instance whose `when` evaluates to false at the end
   of startup begins inactive, with its other cells holding their just-computed
   initial values."* The subtree constructs, then freezes; the constructed values
   are readable and no `eval` follows (RW-7).
2. **the open edge / snap.** The commit a gate opens: the guarded deriveds
   evaluate in that same commit, forced-stale, reading current values — preceded
   by the `gate <path> open` line (**R73 + R75**).
3. **the close edge.** The subtree's last values freeze and stay readable;
   `gate <path> close` appears.
4. **the predicate's one-commit delay.** A write that flips the predicate
   publishes at commit N; the flip and its snap happen at commit **N+1**
   (**R73's literal prior-commit reading**). This witness is the ruling's
   regression guard — it fails under any other reading of fork 3.
5. **frozen while closed — inputs stay live.** Input cells stay live under a
   closed gate: the write IS staged and IS dirty; the guarded derived does NOT
   recompute. The trace shows a `dirty` line with no following `eval` (§4.7).
6. **nested gates.** Inner open, outer closed: effective activation is the AND
   down the `gate_parent` chain; the inner subtree stays frozen; the inner gate's
   own predicate still evaluates and its own state still updates, but no
   `gate` line is emitted for it while the ancestor is closed (**C-39/C-40**).
   Reopening the ancestor restores each descendant to its own state, with no
   replay.
7. **gate × recurrent — the loss witness.** Write to a frozen recurrent's input
   while closed, reopen, and assert the recurrent is still at its pre-gap value
   until a NEW input change arrives (§4.8). The single most important interaction
   witness in cut B.
8. **`reset_on_reopen`.** On the reopen transition the self- and input-history
   clear in step 1a, so the first post-gap evaluation reads FALLBACKS
   (**C-13**) — asserted in the same commit as the reopen, which is what makes
   the step-1a position observable.
9. **gate × deferred — cancellation.** Gate-close cancels the in-flight held run
   (no landing at its due commit); gate-open dispatches a FRESH run at that
   commit's end, landing at +depth (§4.7). Both halves assertable in the trace,
   and `has_staged_work` is false across the cancelled window.
10. **the predicate's own dependencies.** A predicate input changes but the
    boolean result does not: no transition, no `gate` line, no snap.
11. **rank-interleaved roots.** One commit carrying a host write, a gate
    transition and a deferred landing at interleaved ranks: the `dirty` and
    `gate` lines appear in ONE rank sequence (**R76**).
12. **the self-conditional gate LOADS — RULED (a), 2026-08-24; corpus pair
    LANDED (`self_conditional_gate`).** The owner withdrew R73's rider, so this
    witness inverts: it asserts that a §13.9.6-shaped gate whose predicate reads
    a cell it guards **loads and runs**, its predicate reading prior-commit
    values through step 1a — visibly, a transition that trails its own guarded
    change by exactly one commit. Three tests now cover it: one loader unit test
    (the shape LOADS), one engine unit test, and the corpus pair, whose golden
    also pins the CONSEQUENCE of the ruling — such a gate **latches**, because
    the value its predicate reads is the value it froze, so a closed
    self-conditional gate can never reopen on its own.

### 6.4 Property-test extensions

The three landed properties
(`no_cell_evaluates_twice_in_one_commit`,
`every_commit_settles_to_the_naive_recomputation`,
`reversing_each_commits_writes_changes_nothing` —
`crates/ductus-conformance/tests/properties.rs`) all extend:

- **no double evaluation** extends unchanged to recurrents and gate-opened
  subtrees; the generator gains recurrent cells and gates.
- **settles to naive recomputation** needs a richer oracle: the naive
  recomputation becomes a per-commit *sequence*, because a recurrent's value
  depends on the advance count and a deferred's on the commit index minus depth.
  This is the property most likely to need redesign rather than extension.
- **write-permutation invariance** extends unchanged and is the cheapest guard
  that step 1's generalization (R76) did not break rank-order determinism.
- **NEW — lockstep**: no recurrent ever observes another recurrent's
  just-advanced value, so permuting step 4's drain order changes no trace
  (023-35, asserted directly).
- **NEW — advance cadence**: a recurrent's ring advances **exactly once per
  evaluation and never otherwise** (R72 + R77) — the ring's advance count equals
  the cell's `eval` count in the trace.
- **NEW — freeze idempotence**: a graph whose gates are all closed produces a
  trace with no `eval` lines under any write sequence (dirty lines still appear —
  input cells stay live, §6.3's witness 5).
- **NEW — gate-line/state agreement**: the number of `gate <path> open|close`
  lines for a path equals the number of EFFECTIVE activation changes for it
  (C-39/C-40), so the trace never over- or under-reports a nested flip.

**The generator's two recurrent restrictions are OFF (FND-38, discharged in wave
2).** Wave 1's generator structurally guaranteed that a recurrent is reached
before any reader, because the landed schedule was declaration-order dependent —
a narrowing recorded only in a code comment. Under §4.12 the arrangement it
avoided is no longer observable, so both restrictions came off: the generator
draws readers on either side of their recurrent and recurrents fed by computed
cells, and the vacuity guard gained a floor for each of the three shapes. The
engine and the commit-indexed oracle agree across the widened domain, which is
this law's natural regression guard.

### 6.5 Trace-golden implications

Every M0 golden must still pass **byte-identically** — M1 adds constructs, it
does not change the law for a graph that has none. That is the cheapest
regression gate available and it is exit criterion 1 (§10).

The one new line's canonical form is pinned in `trace_event.rs`'s doc comment
exactly as the five existing ones are (§3.5), and R24's minimal-semantic test was
applied to it in R75: observable contract, not implementation shape.

### 6.6 Dual-construction equivalence

Unchanged (M0.md §6): each witness is also built programmatically through
`ductus-ir`'s Rust API and must produce an identical trace. R71's two new clauses
are the one place where a parsed module and a constructed one could diverge —
`lookback` and `fallbacks` are the first clauses whose canonical SPELLING is a
function of their values (§4.9) — so this track earns its keep in M1.

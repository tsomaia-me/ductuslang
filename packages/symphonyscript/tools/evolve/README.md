# evolve

`evolve-probe` compiles hand-written programs and prints what each draws. Run it from `packages/symphonyscript` as `cargo run -q --manifest-path tools/evolve/Cargo.toml --bin evolve-probe -- [--budget <s>] [--jobs <n>] [--values] [--summary] <file>...`. A file holds programs split by lines `----`. A program's first line may be a tag choosing its vocabulary: `#example` (the default, SPEC §1.3), `#native`, `#bounded`, `#envelope`, `#bar`, `#signature` or `#to`; an unknown tag stops the run before any program compiles. `evolve-probe --tags` prints the tag table, a line `<tag> <vocabulary>` per tag. A program's last line may be `#expect <codes>`, the codes it draws joined by spaces in the order the compiler reports them, nothing for a clean program, `panic` or `timeout`. Each program compiles as `main.sym` in its own process, `--jobs` at a time (default 4), and is killed past `--budget` seconds (default 30). Its block is a header `[<index>] #<tag> <file>:<line of its first source line>`, then a line `<code> <line>:<col>-<line>:<col> <summary>` per diagnostic, with `help: <help>` and its related spans indented below it, at positions counted from the program's first source line; `clean` when it draws nothing; its compile time in ms; `panic <message>` or `timeout` instead when it panics or passes the budget. `--values` adds `ok` or `differs: expected …, drew …` to each program with an `#expect` line, and `--summary` ends the run with the number of programs, clean programs, programs with an error, programs with a warning, panics and timeouts, and the `ok` and `differs` counts under `--values`. With this file as `cases.txt`, `evolve-probe --values --summary cases.txt` prints two blocks and `summary: programs 2, …, ok 2, differs 0`:

```
#signature
Clip c | three=([1]):
    Note
#expect
----
Clip c | three=([1]):
    Note
#expect no-entry-instance unknown-attribute
```

## The shared step

`python3 review/run.py shared <tip> [--into <dir>] [--against <commit>] [--exhaustive] [--stress] [--quiet-below <load>] [--jobs <n>] [--pins <record>]`, run from `tools/evolve`, is the head's shared step before a review (`docs/PLAN.md` § Reviews). It exports the tip, builds it in the `dev` profile, runs the four checks, each as a command of its own, the verdict diff and the speed figures, and writes `review-runs/<sha>/manifest.json` beside every log and result. The exhaustive tests run only under `--exhaustive`, after the unit tests, and the stress tests only under `--stress`, after them, as `docs/PLAN.md` § Work and checks says, each with `--no-fail-fast` so every test runs; the manifest's `ignored_tests` records whether each ran, and each is judged against the pinned sets (below). The stress tests and the verdict check wait until the 1-minute load is below the `--quiet-below` load, 6 when the flag is absent and no wait under `inf`, and the manifest's `load_limits` records the load each step waited for. The manifest's `test_times` holds, for the unit run (`nextest`) and for the exhaustive run (`nextest-exhaustive`) when it ran, every test its log reports with its time in seconds and its status, slowest first, a test reported without a time last.

The verdict diff reads each program of `corpora/probes.jsonl.gz` as `evolve-probe` reads a file: the text splits at its `----` lines, a program's first-line tag chooses the vocabulary `evolve-check` checks it under, as `evolve-probe --tags` prints it once per run, and its `#expect` line is dropped. A probe whose tag names no vocabulary is not checked: it takes the verdict `unknown-tag`, and `diff.md` names it with its tag.

Each verdict of `verdicts.jsonl.gz`, a gzip file of JSON lines, holds beside its outcome and its error, warning and signal codes every diagnostic whole, in the order the compiler returns them: its code, file, primary span in byte offsets, summary, help, and each related span with its file and label; on the 96,104 programs at `8627d72` it is about 8.7 MB, 141 MB unpacked, where the codes alone took 1.3 MB and 15 MB. After the code classes of `## Moved`, `diff.md` reports the programs whose outcome and codes are equal and whose diagnostics are not, a section for each kind: moved spans, changed summaries, changed helps, changed related spans, changed order, and a code drawn a different number of times. Diagnostics equal in every field that only trade places are a change of order alone; the others pair by code, the unchanged ones set aside first, and a program counts in every kind it changes in. A section's classes are the codes that differ, a count's with `+` or `-`, each with its SPEC sections and its three shortest programs, their diagnostics before and after at line and column; `diff-full.md` also lists every program of each class. A baseline recorded by an earlier tool carries codes only, so the diagnostics are compared whole only where both records hold them, and the header of `diff.md` states how many programs of equal codes were compared whole and how many by their codes alone, on each side. `python3 review/run.py record <sha>` records `review-runs/<sha>/verdicts.jsonl.gz` as the baseline `<sha>.jsonl.gz` and refuses a run whose records carry codes only: a baseline is re-recorded by a `check` of its commit with this tool, then `record`.

`evolve-check` and `evolve-time` compile each program on a thread under the budget. A compile past the budget is abandoned, and once that program's line is written the process replaces itself with a fresh run of the same command from the next line, appending to the same output, so no abandoned compile runs beside another program. `evolve-time` writes each program's `running_compiles`, the compiles still running when its compile began, and for a compile that finishes its `peak_bytes`, the most bytes its own allocations held at once, and its `allocations`, as `allocation-counter`'s measure counts them on the compile thread.

`evolve-count [--vocabulary <name>] [--nodes] <programs.jsonl> <counts.jsonl>` writes each program's `syntax_nodes`, every node of the parse of each of its sources, and its `expanded_items`, the instances and wires its expansion yields, read as the least `expanded_items_warning` at which the compile draws no expansion warning, null past 1,000,000 or under `--nodes`. `evolve-count --fixture` prints the 10,000-line fixture project, `symphonyscript_fixtures::large_project` (`crates/fixtures/projects/large/`), as one program.

The speed figures, `figures.json`, are the step's last command, after `build-release` builds the evolve binaries in the release profile in the verdict check's export, beside its `dev` build. Every figure is taken in both profiles from that one export: for each figure the `dev` runs, then the release runs, each in one `evolve-time` process of its profile that runs `Compiler::check` on its compile thread, one program at a time, with one job. Each profile's runs wait until the 1-minute load is below the `--quiet-below` load, 4 when the flag is absent and no wait under `inf`, the figures together waiting at most 10 minutes, and record that load beside them. Each figure records, in `dev` and in `release`, its time and its target, `past_target` when the time passes it, and `ratio`, the release median divided by the `dev` median, rounded to two places; its printed line names both profiles and the ratio, and a figure past its target is printed with `PAST TARGET` and listed under `past_target` in `figures.json`. The targets are `docs/PLAN.md` § Reviews' table's: release the promise, and `dev` the table's own `dev` figure where it states one and 1.3 times the release target where it states release alone.

- A compile-time recursive call: a program whose `g` makes 1,000,000 distinct recursive calls over trees of distinct sizes, three runs, the median divided by 1,000,000; 1.7 µs release, 2.24 µs `dev`.
- An inlined call: a program of 10,000 notes, each summing 100 calls `f(i, 0)` to `f(i, 99)` of a non-recursive `fn f(x, k): x + k` on an input, so Resolve and Infer each walk 1,000,000 distinct call sites, three runs, the median divided by 1,000,000; 1.5 µs release, 2 µs `dev`.
- A level of nesting: the deep-expressions fixture at depth 100,000 for each construct alone and for all of them together, three runs each, the median divided by the levels; 1.5 µs release, 2 µs `dev`.
- A program of the breaker corpus: every program of `corpora/breakers.jsonl.gz` checked once in each profile, with the verdict check's budget; a program the verdict check found past its budget is not run again, and it and a program past the budget here rank above every timed one; the median and the 99th percentile by nearest rank over every program; 0.38 ms and 1.5 ms release, 0.5 ms and 2 ms `dev`.
- The figure set's shapes (`work/layout-design.md` § 8.3), each at three doubling sizes, three runs at each, recording at every size the time per unit and the peak bytes and, as `growth`, each size's median divided by the one before it: an expanded item, `Rig r:` / `for i in 0..n:` / `Lamp/(1 + i % 12) | hue=0.5` at 50,000, 100,000 and 200,000 iterations, 0.7 µs an item release and 0.91 µs `dev`; a pattern with a reference parameter used 1,000, 2,000 and 4,000 times; X9's rings of 1,000, 2,000 and 4,000 cells, each cell reading its neighbours' history both ways, a scalar, a fixed-array and a variable-array ring, beside the scalar ring read one way; X8's frame program, 8,000 terms at depths 200, 400 and 800; a placeholder beside a recursion of 1,000, 2,000 and 4,000 distinct calls; a value-shaped body, a 1,000-node body whose parameter bounds a slice, called at 1,000, 2,000 and 4,000 distinct values; and a 1,000-node function called at 1,000, 2,000 and 4,000 sites, each passing its own unannotated derived cell. The shapes other than the expanded item have no target in the table, and their growth is the figure.
- A whole-project recompile: the 10,000-line fixture project, its syntax nodes and expanded items counted by `evolve-count` and printed, three runs, the median against 1 µs a syntax node plus 0.7 µs an expanded item release and 1.3 times that in `dev`.
- Peak memory: the peak bytes of the recompile's runs and of the expanded item's runs at each size, each with its bytes per syntax node and per expanded item, against 256 B a syntax node plus 112 B an expanded item in either profile, the expansion program's items its iterations.

Each per-unit figure counts the program's other text, its lexing and parsing among it, in its time. Only the inlined, the recursive and the nesting programs raise a limit, `inlined_calls` to 1,000,000 with its warning at 500,000, since only the inlined program passes a default, and each figure records the limits it raised.

Each figure program states the codes it must draw: at these sizes `limit-warning` and `no-entry-instance` for the recursive and the inlined programs; `no-entry-instance` for every nesting program and every shape, `limit-warning` beside it for the frame program at depth 800, whose recursion passes the nesting warning at 512, and `unknown-name` beside it for the placeholder; and the fixture project `no-entry-instance` alone, since it places no entry instance. A figure one of whose runs, in either profile and at any size, panics or draws another set of codes, one code more or one fewer, is void: `figures.json` marks it `void` beside the codes it drew and the codes it must draw and lists every void figure under `void`, its line in `figures.log` ends `VOID: drew …, must draw …`, and the command exits 3. The breaker figure states no codes. The shared step prints `figures: exit 3 (a figure is void)` and exits 2 when a figure is void and every other command passed, 3 when a command failed too, 1 when a command failed and no figure is void, and 0 when all passed.

`python3 review/run.py figures <binaries> <check-times.json.gz> <out> [--release <binaries>] [--quick]` takes the figures with the `dev` binaries given and the release binaries of `--release`, or, without it, the release binaries it builds with `cargo build --release --bins` in the export beside the `dev` binaries, the one `run.py check --build <dir>` keeps, into the `release` folder beside them. Under `--quick` it takes the quick figures into `figures-quick.json` beside `<out>`, the figures the head takes at every step's hand-back. Its programs are the full ones at a tenth of their size: the recursive and the inlined programs at 100,000 calls and the nesting programs at depth 10,000, each stating `no-entry-instance` alone, since neither call program reaches a limit's warning value at that size; the expanded item at 5,000, 10,000 and 20,000 iterations, the frame program at depths 20, 40 and 80, and the other shapes at 100, 200 and 400; the fixture project whole. Its breaker figure takes the 200 breakers slowest in the given check times among those timed within the budget, three runs each in one `evolve-time` process per profile, the median and the 99th percentile over each program's median, a program past the budget in any run ranking above every timed one. A void figure is recorded, printed and exits 3 as in the full figures.

## The pinned sets

`review/pinned.json` holds a pinned set for each test that fails at a known set of rows: under `tests`, the test by its nextest name, `<binary id> <test name>` as nextest's status lines print it, with `count`, its failing programs' number, and `rows`, each failing program's text as `program` and its whole diagnostics as `diagnostics`, sorted by program. The shared step judges its exhaustive and its stress run against it: a pinned test whose failing set equals its record, program for program and diagnostic for diagnostic, passes; one that gains a program, loses one, or draws other diagnostics for one fails, naming each program that joined, left or changed, a changed one with its diagnostics before and after; a pinned test that passes fails, naming every program that left; a pinned test that fails with no row the tool reads, or that does not run, fails; and a failing test with no pinned set fails as before. Each judgement is appended to the run's log under `pinned sets (<record>):`, a line `<test>: pinned: <n> programs, unchanged` for a test that holds its set, and recorded in the manifest's command as `pinned`, with the step's `exit` the judged one and `nextest_exit` nextest's own; a step whose nextest exit is not 0 and whose log names no failing test fails too.

The tool reads a failing program from the test's output: one line per failing row, `pinned-row ` and then a JSON object on that line, `{"program": <the row's source text>, "diagnostics": [<each diagnostic whole, in the compiler's order, as {"code", "file", "span": [start, end], "summary", "help", "related": [{"file", "span", "label"}]}>]}`, printed on the test's standard output or error or in its panic message, before nextest's summary. A program printed twice counts once, its first row.

`python3 review/run.py pin <test>... [--log <nextest log>] [--package <dir>] [--pins <record>]` records each named test's current failing set as its pinned set: from the given log, a shared step's `nextest-exhaustive.log` or `nextest-stress.log` among them, or else by running `cargo nextest run --workspace --run-ignored all --no-fail-fast` over exactly those tests in the package, this checkout's by default. A named test that passes is unpinned; one that fails with no row the tool reads, or that is not in the run, refuses the whole command and writes nothing.

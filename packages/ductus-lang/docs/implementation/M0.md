## 1. Mission

Build the runtime kernel that loads a hand-written `.duir` module and runs the write→commit→read loop with spec-exact semantics for the smallest useful slice: `input` and `derived` cells inside static scopes. No frontend, no CLI. Every semantic claim is asserted by a commit-trace test against a hand-written expectation. This is the first implementation-as-audit probe of §13.

## 3. Architecture

Cargo workspace at `packages/ductus-lang/` per STRATEGY §4-H. M0 creates three crates plus the corpus tree (R8); `ductus-frontend`/`ductus-cli` are created at their own milestones.

```
crates/
  ductus-ir/        # graph-spec + behavior-table TYPES, .duir text parse + emit (both directions)
  ductus-runtime/   # loader, cell store, commit engine, snapshot, trace
corpus/
  duir/m0/*.duir    # hand-written modules
  duir/m0/*.trace   # expected commit traces (golden)
```

Three seams, pinned day one (STRATEGY §4-C guardrails):

1. **Behavior provider.** The loader takes `&dyn BehaviorProvider` resolving `BehaviorHandle → executable`. M0's sole implementation is the test-harness stub registry (`register(handle, closure)`), per the §4a-1 ruling. The behavior table (`hash → executable`) is the only codegen point in the system, ever; the runtime is otherwise pure data.
2. **Trace sink.** The commit engine emits trace events through a sink trait; tests capture, production uses a no-op. The trace is route-independent by construction (values and order only, no timing, no pointers) because the dual-route equivalence law (STRATEGY §2.4) asserts trace identity across routes.
3. **Storage.** M0 stores word-sized values in-cell with double-buffered previous/current per cell and an atomic snapshot flip (SPEC §14.3 model, word tier only). The `Value` enum spans exactly the M0 type tags.

Strictly sequential core (STRATEGY §2.4a): no threads anywhere in M0, including the harness.

## 4. Semantics contract (M0 subset of §13.10.2)

`commit()` performs, in order — the normative step list is SPEC §13.10.2; M0 implements it with only input/derived cells present:

1. **Dirty set.** Per writable cell: staged value ≠ previously-committed value ⇒ dirty (reverted intermediate writes ⇒ not dirty). Dirt propagates transitively through derived dependency edges. No new dirt after this step.
2. **Evaluation order.** Topo-sort the per-commit DAG of dirty deriveds; ties between same-instance nodes break by declaration order, and the cross-instance/composed total order per §13.10.3.
3. **Evaluate.** Invoke each behavior via the provider with its input-cell values (signal reads → staged values; derived reads → this-commit values if evaluated earlier, else previous-committed). Results write the pending snapshot. Value-change gating applies on outputs: an equal result propagates no dirt downstream.
4. **Advance recurrents.** No-op in M0 (structural placeholder retained so M1 lands in place).
5. **Publish.** Atomic snapshot flip; observers' subsequent reads see the new state.
6. **Clear dirty bits.**

Writes during a commit are forbidden (assert). Writes between commits accumulate. A commit with no dirty cells publishes an identical fresh snapshot (idempotence, §13.14.4). `transaction` is host sugar over staged writes (§13.10.4) — same commit path.

## 5. The behaviors question (mechanics of the §4a-1 ruling)

IR_GRAMMAR's module-resolvability note makes a graph referencing `B@xx` with no defining behavior a load-time error. M0 modules carry `behaviors {}` (no behavior-body compiler exists yet), so the loader's resolvability check runs against **module table ∪ provider registry**: a handle satisfied by either resolves; satisfied by neither → the existing load-time diagnostic. This is the test-harness seam the owner ruled, expressed as loader policy — not a corpus change. When behavior-body IR lands (the cranelift milestone), module-carried bodies join the same table and the dual-route law becomes fully assertable; the reference interpreter enters as the differential oracle at that milestone, not M0 (there are no behavior-body instructions to interpret in M0).

Stub signature: `Fn(&[Value]) -> Value` — matching the behavior ABI row for `derived` (SPEC §15.4.4: input-cell current snapshot values in, new value out). Stubs must be pure; the harness cannot enforce it, the test author must.

## 6. Test plan (STRATEGY §4-G tracks, mapped to M0)

- **Commit-trace goldens** — the M0 workhorse. Each `corpus/duir/m0/*.duir` pairs with a `.trace` expectation; the harness loads, registers stubs, drives a scripted write/commit sequence, and byte-compares the emitted trace. Minimum witness set: single derived; diamond (glitch-freedom — one evaluation per commit, correct joined value); chain (topo depth); value-change gating (write of equal value ⇒ no evaluation; reverted write ⇒ not dirty); same-level tiebreaker order; multi-write transaction; empty-commit idempotence; independent islands (both settle in one commit); trap (path-bearing abort).
- **Round-trip byte stability** — `emit(parse(text))` is byte-identical to canonical text for every corpus file.
- **Dual-construction equivalence (M0 seed of the dual-route law)** — each witness is also constructed programmatically via `ductus-ir`'s Rust API; parsed-vs-constructed modules must produce identical traces. (The full law needs a frontend; this seeds the harness shape.)
- **Semantic property tests** — randomized DAGs + write sequences asserting: no cell evaluates twice per commit; no evaluation reads a stale dependency; trace is identical under permutation of same-commit writes to distinct cells.
- **Diagnostics** — F3 registry enum from day one; tests assert class ids, never message strings. M0 classes: unresolvable behavior handle, unknown input path, duplicate cell path, kind/feature outside the M0 slice, write-to-non-input, write-during-commit, type-mismatched write.

## 7. Exit criteria

1. All §6 witnesses green; property tests green.
2. `.duir` parser accepts the full IR_GRAMMAR module/types/graph sections; loader rejects out-of-slice constructs with named diagnostics (grammar-complete parser, slice-checking loader — F4's over-admit/legality split applied to the IR).
3. Round-trip byte stability holds corpus-wide.
4. Zero unruled divergences: every implementation-vs-corpus contradiction discovered is filed in `docs/implementation/FINDINGS.md` (numbered-atomic) and either ruled or explicitly parked by the owner.
5. The three seams exist as traits with the M0 implementations behind them (provider, sink, storage).
6. Workspace scaffolding: three crates (R8), corpus tree, CI running the harness.

## 10. Expected divergence probes (predicted findings — file, don't resolve)

These are places where M0 will likely surface corpus gaps. Per the divergence protocol (STRATEGY §2.3), each becomes a FINDINGS.md entry + owner ruling; no code workarounds.

1. **Tiebreaker carrier.** §13.10.3 breaks ties by *source declaration order* (and placement order across instances) — but what carries that order into the IR? Probable answer: graph-section entry order is normative. If the corpus doesn't say so, that's finding #1.
2. **Float equality for value-change gating.** Step 1 compares values for identity; IEEE `NaN ≠ NaN` would make a NaN-holding cell perpetually dirty. Bitwise equality is the self-consistent candidate — needs a ruling the moment a float witness exists.
3. **`behaviors {}` resolvability wording.** IR_GRAMMAR's note doesn't know about provider-supplied behaviors; if D5 stands, the note may deserve a conforming touch-up (ruling either way).

- **L1** Eager lexing: whole file → `Vec<Token>` + index cursor (files are small; trivially peekable/backtrackable). Not a streaming iterator.
- **L2** Tokens own their payloads (`Ident(String)`, `Int(i64)`, …) — no lifetimes threading lexer→parser; comprehension over micro-cost (consistent with R6).

Parser:
- **P1** Parse directly into the `ductus-ir` graph AST (T1) — no CST/parse-tree layer; the text form is a serialization, not a human document; formatting is canonical by definition.
- **P2** `Parser` struct holding cursor + diagnostics; ONE function per grammar production, function names mirroring IR_GRAMMAR production names 1:1 (grammar↔code correspondence as a review tool).
- **P3** Spans carried on named AST entries (scopes, cells, behaviors) — enough for load-time diagnostics to point into the file — not on every leaf.
- **P4** To verify at increment 3 (never from recall): whether the `.duir` text form admits comments; if yes, round-trip byte stability is defined over canonical (comment-free) form and corpus files must be canonical.

Emitter:
- **E1** The emitter IS the canonicalizer: one true rendering (fixed indent, fixed clause order per grammar); the round-trip gate `emit(parse(f)) == f` therefore also enforces that every corpus file is written in canonical form.
- **E2** Plain string-building with an indent counter; no formatting engine.

Loader:
- **LD1** Static evaluation order at load (E2 axis) via Kahn's algorithm; the composed tiebreaker realized as each cell's graph-section ENTRY INDEX used as tiebreak rank — explicitly resting on divergence probe #1 (§10.1): file the finding at this increment and get the ruling that entry order is the normative carrier.
- **LD2** The loader is the sole legality authority (F4): parser over-admits grammar; loader owns duplicate-path, unknown-input, slice, resolvability (D5), and cycle checks — a derived-graph cycle is a load error in M0 (nothing exists yet to break cycles), reported with the cycle's member paths.

Store:
- **ST1** Snapshot in M0 is a borrow-view (`Snapshot<'_>` over the store): zero-copy, and the borrow checker itself enforces "no writes while a snapshot is alive." The concurrent snapshot of later milestones arrives behind the same API name.

Engine:
- **EN1** `commit()` decomposes into functions mirroring §13.10.2's six steps 1:1, in step order, each carrying its § anchor comment; `advance_recurrents` exists as an explicitly-empty step 4 so M1 lands in place.
